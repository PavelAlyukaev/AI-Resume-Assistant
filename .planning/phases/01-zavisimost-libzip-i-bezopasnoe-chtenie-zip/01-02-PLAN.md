<objective>
Classify every non-DOCX and damaged input by its bytes, before any part is read, and read the three DOCX parts from memory with a clear error code for each failure. Plan 01-01 gave the ZIP wrapper; this plan adds the container layer that decides what the bytes are.

Purpose: SAFE-01 at the documents layer. A non-ZIP text file, a truncated ZIP, an encrypted DOCX (which Word stores as an OLE2 container, not a ZIP), an old .doc renamed to .docx, and a ZIP without the main part must each produce a distinct code. The documents layer returns codes only; user-facing Russian texts and the file name are the application layer's job (plan 01-03).

Output: DocxTypes.h with the full code and limit vocabulary, DocxContainer with the classification and part reading, tests for every code, shared fixtures in tests/DocxFixtures.h, and the layer README.

Tracer: Task 1 is the leading tracer. It runs one path end to end through the layer (bytes in, ZIP classification, ZipArchive read, DocxParts out) and is tested through the public function. Tasks 2 and 3 widen it to the remaining codes and to the defensive checks.

Reversibility: the DocxParts shape is consumed by Phase 2 and the DocumentImport result by Phase 3, so the shape is rated costly and flagged on Task 1. The codes and the limit values are reversible constants. No one-way decision is made here and no checkpoint is inserted.

Decisions implemented here (see 01-CONTEXT.md): D-06 (separate codes for LegacyDoc and Encrypted, and a distinct code for Corrupt, NotZip and MissingPart), D-07 (a damaged part fails the whole read; no partial result), D-08 and D-09 (missing optional parts produce warnings in the result, and the UI shows them later), D-10 (only the three named parts are read, and nothing is written). D-01 and D-03 values are pinned in DocxTypes.h; D-01 is enforced at the file level in plan 01-03. D-03 is enforced in Phase 2.

Unit and scope note (flagged for owner confirmation): the "MB" in D-01 and D-02 is read as MiB (1024 times 1024 bytes). D-02 is reinterpreted: it names only word/document.xml, while this plan applies one 20 MiB budget shared by word/document.xml, word/styles.xml and word/numbering.xml in one open. The reinterpretation awaits owner confirmation and is recorded in plan 01-04.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-selected file bytes to readDocxParts | Untrusted bytes; classification happens before any libzip call that could misread them |
| ZipArchive to DocxContainer | Only codes and byte arrays cross this boundary; no libzip type and no message text |
| CFB bytes to the EncryptedPackage search | Untrusted bytes scanned linearly with bounds-checked search; no offsets are taken from the file |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Spoofing | Non-DOCX input (text, renamed .doc, other formats) accepted as DOCX | medium | mitigate | Magic-byte classification before any libzip call: ZIP local header or empty-archive record goes to ZipArchive; CFB signature goes to the CFB branch; everything else is NotZip. Tests cover text, zero-byte and CFB inputs. |
| T-01-06 | Tampering | Encrypted or legacy containers read as DOCX text | medium | mitigate | EncryptedPackage UTF-16LE search decides Encrypted versus LegacyDoc; a libzip password-required entry maps to Encrypted. Tests cover both CFB variants and a libzip-encrypted entry. |
| T-01-07 | Information Disclosure | Partial document text returned after a damaged part | medium | mitigate | Any entry read failure returns an error code only (D-07). The corrupted-entry test asserts no bytes are returned. |
| T-01-08 | Tampering | Out-of-bounds access while scanning CFB bytes | low | mitigate | The scan uses bounds-checked QByteArray search and never takes an offset from the file. |
| T-01-SC | Tampering | Package install (supply chain) | high | accept | This plan installs no package. The libzip package gate is in plan 01-01 Task 1. |
</threat_model>
