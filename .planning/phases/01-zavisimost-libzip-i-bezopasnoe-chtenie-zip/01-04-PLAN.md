<objective>
Stop the zip-bomb and header-forgery cases that SAFE-02 names: an entry that expands far beyond its compressed size, an archive with too many entries, duplicate names that could hide the real main part, and declared sizes that lie about what the entry will produce. Every control counts bytes actually produced or entries actually present; no control trusts a header value alone (research Pitfall 3, Pitfall 6).

Purpose: SAFE-02 completion. Plans 01-01 and 01-02 already count bytes against the budget during reads; this plan adds the ratio control, the structural controls at open, and the tests that show each limit fires at its exact boundary.

Output: ZipArchive ratio and structure checks, DocxContainer budget sharing with a test seam, fixture helpers for forged headers and many entries, bomb tests at both the archive and the application level, and the phase gate with the memory journal entry.

Tracer: Task 1 is the leading tracer. It runs one bomb file from a Cyrillic directory through DocumentImport, ZipArchive ratio check and libzip, and checks the Limit text.

Reversibility: the numeric limits (1000 entries, 100 to 1 ratio, 1 MiB threshold, 20 MiB budget) are planner choices recorded in DocxTypes.h. They are reversible constants and are listed in the memory note for owner confirmation (STATE.md blocker: choose one set; this plan chooses it). No one-way decision is made here.

Decisions implemented here (see 01-CONTEXT.md): D-02 (one 20 MiB budget for all parts in one open, counted on bytes produced), D-07 (any limit or read failure returns an error, never a partial result), D-10 (the archive is read-only and nothing is extracted to disk).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| central directory and entry headers to ZipArchive | Declared counts, names and sizes are attacker-controlled and are never trusted for allocation or for the budget |
| entry data to the output buffer | Bytes produced by decompression are the only quantity counted against the budget |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-12 | Denial of service | Zip bomb: small compressed entry expands far beyond its size | high | mitigate | Ratio check after 1 MiB against the declared compressed size (100 to 1), plus the 20 MiB budget on produced bytes and 64 KiB chunked reads. Tests: deflated bomb rejected; stored large entry accepted. |
| T-01-13 | Tampering | Forged declared sizes to bypass the budget or to force a large allocation | high | mitigate | Budget counts bytes returned by reads; declared sizes only feed the ratio check and are never used to reserve memory. Test: declared size smaller than the data yields Corrupt or a bounded result. |
| T-01-14 | Denial of service | Central directory with excessive entries | medium | mitigate | More than 1000 entries returns Limit at open, before any entry is read. Test: 1001 entries rejected; 1000 accepted. |
| T-01-15 | Tampering | Duplicate names or case and suffix variants selecting the wrong part | medium | mitigate | Any duplicate name is Corrupt; lookup is exact, case-sensitive, and without the case-insensitive flag. Tests: duplicate rejected; variants do not match. |
| T-01-SC | Tampering | Package install (supply chain) | high | accept | This plan installs no package. The libzip package gate is in plan 01-01 Task 1. |
</threat_model>

If the valid flags report that the compressed size is known, keep it as the declared compressed size; otherwise use the value 1, which makes the ratio check stricter and fails closed. (3) tests/DocxFixtures.h: make the libzip writer set the compression of each entry to deflate explicitly, so the bomb fixture is deterministic on every build. Other fixtures are unchanged in behavior.

(4) tests/ZipArchiveTest.cpp: add deflatedBombIsLimitedByRatio. Build a libzip archive into the ASCII scratch directory with one entry named word/document.xml that holds two mebibytes of zero bytes.
